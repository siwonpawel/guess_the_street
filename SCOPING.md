# Guess the Street — Scoping Plan

A browser game: at game start you pick a city, the game secretly picks one named
street in it, and you click on the map (OpenStreetMap street layers only — no
satellite/aerial imagery) where you think that street is. After each guess you
get a summary of how far off you were ("you missed by 137 m"), plus a score.

**Hard constraint: no backend.** The game is a fully static site — HTML/CSS/JS
plus static data files, deployable to any static host (GitHub Pages, Netlify,
Cloudflare Pages). The only network calls at runtime are map tiles and (optionally)
pre-fetched data files served from the same origin.

---

## 1. Game concept and rules

1. **Game start — city selection.** Player picks a city from a curated list
   (searchable grid of city cards: name, country, number of streets in play).
2. **Round setup.** The game randomly picks one named street (target) inside the
   city bounding box. The player is told the target's name, e.g. *"Find:
   `Rue de Rivoli`"*.
3. **Guessing.** The map shows only street layers (streets, optionally labels —
   see difficulty toggle below). The player pans/zooms and clicks once on the
   street they believe is the target. One click = one guess, no re-guessing.
4. **Result summary ("how much you missed").** The map reveals the target street
   highlighted, the guess marker, and a straight line between the guess point and
   the nearest point on the target street. Text summary: distance missed in
   meters/km, points scored this round, running total. Button: *Next round*.
5. **Game end.** After N rounds (default 5, distinct streets), a final summary:
   total score, per-round breakdown (target, missed-by distance, points), best
   score stored in `localStorage`. Button: *Play again* (same or new city).

### Scoring

Distance `d` = distance from the clicked point to the nearest point on the target
street polyline (point-to-segment over all segments, computed in a local
equirectangular projection — accurate enough at city scale).

- `d <= 25 m` → "bullseye", full 1000 points.
- Otherwise `points = round(1000 * max(0, 1 - d / D))` where `D` = configurable
  "city scale" (default: half the city bbox diagonal, so a guess at the far edge
  of the city scores ~0). Tunable constant in one config file.

This directly answers "how much you've missed": the result screen is built around
the distance, not just points.

### Difficulty toggle (per game, set at city select)

- **Normal:** street labels visible (CARTO Positron `light_all`). Challenge is
  finding the right street among many similarly-named ones / in the right
  district.
- **Hardcore:** labels hidden (CARTO Positron `light_nolabels`) — pure street
  geometry. The target name is still given, but you must recognize the street by
  its shape, width class, and surroundings. This is the "street layers only"
  mode in its purest form.

## 2. Scope

### In scope (MVP)

- Static frontend app, no backend, no accounts, no build-time server.
- City selection screen over a curated city list (~20 cities to start).
- Per-city street data shipped as static GeoJSON, loaded lazily on city pick.
- Random target street per round, 5 rounds per game.
- Leaflet map with street-only basemap (CARTO Positron, labels on/off toggle).
- Click-to-guess, distance-to-target computation, result summary with revealed
  target street + guess marker + connecting line + missed-by distance + points.
- Final score screen, best score in `localStorage`.
- OSM/CARTO attribution on the map (required by ODbL / CARTO terms).
- Responsive enough for desktop and mobile (tap to guess).
- Deploy: `npm run build` → `dist/` → any static host; GitHub Actions workflow
  for GitHub Pages.

### Out of scope (explicitly not now)

- User accounts, global leaderboards, any server-side storage.
- Live Overpass queries at runtime as the primary data source (kept only as an
  optional dev-time fallback, see §4).
- Multiplayer / shared seeds / daily challenge with server verification.
- Satellite or street-view imagery of any kind.
- Route/POI layers, turn-by-turn anything, geocoding search (city list is static).
- i18n beyond English street names as they appear in OSM.
- Custom vector-tile pipeline (raster tiles + GeoJSON are enough for MVP).

### Post-MVP ideas (parked)

- More cities (100+), generated by the same script.
- Timed rounds, streak bonuses, difficulty tiers by street class.
- "Nearest guess wins" 1v1 hot-seat mode.
- PWA/offline support (precache tiles is against tile usage policies — skip).

## 3. Architecture (static-only)

```
browser ──tiles──▶ CARTO basemap CDN (basemaps.cartocdn.com)
    │               (street-only raster tiles; attribution required)
    └─fetch──▶ same origin: /data/cities/index.json, /data/cities/<slug>.geojson
                (pre-baked OSM street data, static files in dist/)

build time: scripts/fetch-streets.mjs ──▶ Overpass API ──▶ public/data/cities/*.geojson
```

- No API calls to openstreetmap.org at runtime in the shipped game. All OSM data
  is baked into static files at build/deploy time by a script (run manually or in
  CI), which removes runtime dependency on Overpass availability/rate limits and
  keeps the game truly static-hostable.
- App is a single-page app with a tiny hand-rolled state machine:
  `CitySelect → Loading → Round → Result → (next Round | GameOver)`.
- All game state (current city, rounds, guesses, score) lives in memory +
  `localStorage` (best score only).

### Tech stack

| Layer | Choice | Why |
|---|---|---|
| Build | Vite + TypeScript (vanilla, no UI framework) | Smallest bundle, zero framework lock-in, fast static build |
| Map | Leaflet (`leaflet` npm) | Lightweight, plugin-friendly, works with raster tiles |
| Basemap | CARTO Positron `light_all` / `light_nolabels` raster tiles | Street-only cartography (no imagery), free tier OK for low traffic, has a no-labels style for hardcore mode |
| Data prep | Node script + Overpass API (`scripts/fetch-streets.mjs`) | Runs at build time only |
| Geometry utils | hand-rolled (haversine + point-to-segment) or `@turf/turf` | distance calc is ~30 lines; use turf only if bundle size is a non-issue |
| Deploy | GitHub Pages via GitHub Actions (or Netlify/Cloudflare Pages) | static `dist/` |
| Tests | Vitest for pure logic (distance, scoring, street picking) | map UI itself untested in MVP |

## 4. Data strategy (the key decision)

Two options were considered:

| | A. Runtime Overpass queries | B. Pre-baked static GeoJSON (recommended) |
|---|---|---|
| How | App queries `overpass-api.de` when a city is picked | `scripts/fetch-streets.mjs` runs at build time, output committed/served as static files |
| Pros | Always fresh data, no storage | Works fully static, no CORS/rate-limit/uptime risk, instant load, cacheable, works offline-ish from CDN cache |
| Cons | CORS OK but rate limits & latency hurt UX; big-city queries are heavy; game breaks if Overpass is slow/down | Data goes stale (acceptable for a game); repo/host storage grows with city count |
| Verdict | Fallback/dev only | **Primary** |

**Decision: B.** The script queries Overpass per city bbox:

```
[out:json][timeout:60];
way["highway"]["name"]({{bbox}});
out geom;
```

then keeps only named ways with a routable highway class
(`motorway`…`residential`, plus `pedestrian`/`footway` optionally), simplifies
each polyline (Douglas–Peucker, tolerance ~5–10 m), quantizes coordinates to
~5 decimal places, and writes compact GeoJSON (`FeatureCollection`, one Feature
per street with `properties: { name, highway }`). Target size per city file:
≤ 1–2 MB so it loads fast and parses without jank; if a big city exceeds that,
raise simplification tolerance or drop the lowest street classes.

At runtime the app fetches `index.json` once and `<slug>.geojson` only when that
city is picked. Random target = uniform pick over the FeatureCollection (avoid
duplicate-name confusion by allowing duplicates — that's part of the game — but
never pick the same street twice in one game).

**Attribution:** map and data screens must show `© OpenStreetMap contributors`
(ODbL) and `© CARTO` — non-negotiable, put it in the map corner and the footer.

## 5. Map and interaction details

- `L.map` with `zoomControl`, `attributionControl` (prefixed with the required
  credits), initial view = city bbox (`map.fitBounds`), min/max zoom clamped to
  city scale.
- Basemap URL templates in `config.ts`:
  - normal: `https://{s}.basemaps.cartocdn.com/light_all/{z}/{x}/{y}{r}.png`
  - hardcore: `https://{s}.basemaps.cartocdn.com/light_nolabels/{z}/{x}/{y}{r}.png`
  (swap tile layer on toggle; no imagery styles are used at all).
- Guess: single click/tap → `latlng` stored → immediately compute distance to
  target and go to Result (no confirm dialog on desktop; on mobile a small
  "Confirm guess" pin button avoids accidental taps — decide during M3).
- Result reveal: `L.polyline` of target street in accent color + circle marker at
  nearest point on it + marker at guess + dashed line between them; `fitBounds`
  to both points with padding. Summary panel shows: target name, missed-by
  distance (formatted: `< 1 m` → "on the street!", meters, or km with 2 decimals),
  points, total.
- City GeoJSON is **not** drawn on the map during the round (the basemap already
  shows streets; drawing our copy would double-render). It is used only to pick the
  target and compute distances. (Optional post-MVP: toggle "show all candidate
  streets" for debugging.)

## 7. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Overpass rate limits / downtime during data generation | Can't refresh city data | Pre-baked data means runtime never depends on Overpass; use mirror instances (`overpass.kumi.systems`), add retry/backoff in the script, commit generated files |
| City GeoJSON too large → slow load/parse | Jank on city select | Simplify + quantize in script; per-city lazy loading; measure each file, cap ~2 MB; gzip/brotli by host |
| Tile provider terms (CARTO free tier, OSM tile policy) | Tiles blocked if traffic grows | Low-traffic game is fine; keep attribution; config makes tile URL a one-line swap (e.g. to self-hosted or OSM standard tiles) |
| Distance math edge cases (antimeridian, poles) | Wrong "missed by" | Cities are mid-latitude; local equirectangular projection per city is fine; unit-test `geo.ts` |
| Accidental guess on mobile | Frustration | Confirm-pin on touch devices (M3) |
| Duplicate street names in a city | Ambiguous target | Allowed by design (any matching street could be intended) — but reveal shows exactly which one was picked; consider disambiguating with district hint post-MVP |
| OSM data staleness | Target street renamed/closed | Acceptable for a game; refresh = re-run script |
